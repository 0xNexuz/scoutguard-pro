## Historical discovery and conservative decisions

`BlockscoutClient.getSenderHistory(chainId, sender, limits?, budget?)` follows API v2 `next_page_params` from the address `transactions` and `token-transfers?type=ERC-20` endpoints. See the [official REST API documentation](https://docs.blockscout.com/devs/apis/rest). It copies bounded scalar cursor parameters into the same chain-specific route; cursors cannot change host, API key, or token type. A terminal page must explicitly return `next_page_params: null`. Repeated/malformed cursors stop that source and disclose truncation. Pages alternate between sources. Deterministic ordering assumes fixed provider responses; this is not a block-pinned snapshot and new indexed activity can move pagination.

| Bound | Default | Maximum accepted history option |
|---|---:|---:|
| Pages per endpoint | 3 | 20 |
| Inspected records across endpoints | 300 | 2,000 |
| History request attempts | 8 | 40 |
| History duration | 10 seconds | 20 seconds |
| Overall evaluation calls | 12 | Fixed in engine |
| Overall evaluation duration | 10 seconds | Fixed in engine |
| Individual provider request/body timeout | 4 seconds, reduced by remaining deadline | Fixed default |
| Provider response bytes | 2 MB | Fixed |
| Request starts per process | At most 4/second (250 ms spacing) | Fixed default |

Engine-wide call/time budgets remain binding even if a larger history option is supplied. Defaults permit at most six history pages; page size is provider-controlled, and the 300-row cap can stop earlier. Provider calls include attempted dispatches that can be refused by a deadline. No automatic retries occur. A critical engine failure aborts queued/in-flight sibling requests instead of continuing to spend the remaining budget. `maxAgeDays` is optional; any age exclusion is disclosed and prevents an exhaustive-history claim. Operators can configure `new ScoutGuard({ historyLimits: { maxPages: 2, maxRecords: 200, maxProviderCalls: 4, maxDurationMs: 8000, maxAgeDays: 365 } })`. HTTP clients cannot raise these bounds. Four starts/second is a local ceiling, not a guarantee that a shared multi-instance key satisfies every plan's quota; lower limits to the actual plan and use shared coordination before scaling.

Only successful, positive outgoing native transfers or positive outgoing ERC-20 **event** senders establish comparison references. Incoming-only activity, self transfers, zero values, failed/pending native transactions, malformed records and unrelated addresses cannot establish an outbound reference. Native transaction hashes are deduplicated; token events are deduplicated by chain/hash/token/log index. Missing log indexes use a conservative event fingerprint and disclose incomplete evidence. Distinct token contracts and log indexes remain distinct events. All historical token contracts are observations, not a verified token registry or an allowlist.

`source: CONFIGURED` means an operator-supplied reference. `source: BLOCKSCOUT_HISTORY` means observed activity, never verified trust. `verifiedSince` is retained for compatibility; for observed entries it is an observation timestamp, not a trust date. Configured entries can have a `chainId`; entries without it retain the existing all-configured-chains behavior. A token event does not prove top-level transaction initiation (`initiatorVerified: false`). Incoming and zero-value records remain classified in evidence, outside the outbound comparison set.

`evaluation.history.coverage` includes per-endpoint page counts, inspected rows, unique outbound counterparties, outgoing native/token counts, duplicate count, incoming-only address and zero-value counts, completion/truncation, stop reasons, time/request exhaustion, sanitized provider errors, fetch time, observed timestamp range, sender, chain and effective limits. Missing metadata produces `INCOMPLETE_EVIDENCE`. These timestamps describe the lookup and returned rows, not finality or full index freshness.

Both first-page envelopes are critical. Missing either produces `BLOCK` with `SEC-FAIL-CLOSED`; coverage remains available when discovery itself fails. Later-page errors, limits, malformed rows or age exclusions preserve valid partial observations but add `SEC-HISTORY-INCOMPLETE` (`WARN`, 25 points). This prevents PASS, including for exact configured matches; another failing check or accumulated score can raise FLAG to BLOCK. A successful empty scan says only that both indexed endpoints ended without usable references. Even `paginationComplete: true` describes the inspected endpoints at lookup time, not proof that no collision exists anywhere, including internal transactions, other chains or unindexed activity.

## Similarity correctness and payment invariants

All valid distinct references are evaluated before selecting a result. Rank: CRITICAL, SUSPICIOUS, exact match, then no finding. CRITICAL means at least four matching leading **and** four trailing hex characters on different addresses and always blocks. SUSPICIOUS means at least four leading **or** five trailing characters and requires review. Ties use total matched length, prefix length, then lowercase address. An observed exact match cannot hide a later critical resemblance. These are deterministic heuristics, not calibrated probabilities; coincidental similarities and false positives remain possible.

Canonical Ethereum/Base USDC direct `transfer(address,uint256)` behavior is retained. Beneficiary checks use the decoded recipient; token verification uses the transaction destination. Raw integer amounts, six-decimal USDC thresholds and uint256 boundaries are tested. Unsupported selectors, `transferFrom`, trailing/truncated/noncanonical calldata, cross-chain contracts, nonzero native token value, contradictory raw/destination/value assertions, zero recipient/amount and invalid native uint256 values fail closed. Zero-value calls are outside the supported payment scope. The formerly unused recipient-allowlist policy now checks the effective recipient. Hourly volume accounting is still unimplemented.

## HTTP abuse controls and secrets

The public Ethereum route retains five requests/minute/client and gains twenty attempts/minute/process, two active public evaluations, provider budgets, process-wide provider spacing, and a thirty-second provider-failure cooldown. Rejections use 429/503 and Retry-After. These controls are **process-local**, including cooldown and provider spacing; cold starts and multiple Vercel instances do not share them. Deliberately no result cache is used: decisions and failure responses are `no-store`, so an old PASS cannot be reused by an HTTP cache. Recorded research responses retain their existing explicit one-hour cache.

Inputs use strict types and bounded strings, a 16 KB JSON limit, no compressed bodies, no unknown transaction fields, and no numeric coercion. Raw assertion fields are checked rather than silently discarded. Direct Node deployments ignore forwarded client IPs; Vercel enables the existing one-hop convention only when `VERCEL=1`. An external reverse proxy must be reviewed before changing that setting. Aggregate limits still bound a process if per-client attribution fails. Production must be checked anonymously after an approved deployment; a READY label is insufficient.

The protected route always requires its service key, including local use; an absent key no longer opens that route. Production still requires both keys and refuses disabled TLS verification. Errors expose fixed codes/messages, never provider bodies, URLs with keys, authorization headers, or fetch error strings. Application logging contains no request bodies or credentials. Hosting/proxy logging redaction remains an operator responsibility. `LIVE` denotes an attempted live evaluation, including fail-closed results; `source` accurately distinguishes `BLOCKSCOUT_PRO` from the no-key `BLOCKSCOUT_PUBLIC_API` path. Tests and browser fixtures are not evidence of live access.

The dependency audit found GHSA-27r3-jxmh-p828 in body-parser 1.20.8. The lockfile changes only body-parser to 1.20.9. Compressed JSON is also rejected before decompression. The final audit reported zero known vulnerabilities; this is not a complete security audit.

## Receipt verification and replay integration

`ReceiptSigner` keeps its compatibility name. Receipts now carry `policyVersion`, full `checks`, `historyCoverage`, and `integrityAlgorithm: SHA-256-UNKEYED`. Deterministic recursively sorted JSON hashes all returned fields except `integrityHash`: exact chain, sender, transaction destination, decoded beneficiary, token, asset, raw/display amount, original native value, calldata, agent, decision, score, timestamp, checks and evidence. `new ReceiptSigner().verifyReceipt(receipt)` works after JSON round-trip and detects changes relative to the recorded digest. Eighteen independent mutations are tested. Old receipts are historical artifacts and are not silently reinterpreted under the new digest format.

An unkeyed digest does **not** authenticate ScoutGuard; an attacker can recompute it. A future safe authentication design would use a versioned canonical envelope, server-side Ed25519 signing via a managed secret/KMS, public key IDs/rotation, expiry and client transaction comparison. No signing key or infrastructure was introduced. Existing receipts also do not bind nonce/gas or authorize arbitrary contract calls. A real signing agent must use a trusted connection, require PASS and executionAllowed, compare every intended payment field, enforce its own freshness limit, and never interpret a modified/replayed receipt as authorization.

The PC replay task can consume the additive typed `SenderHistory`, `CounterpartyEvidence` and `HistoryCoverage` interfaces in `src/types/index.ts`. Existing evaluation and `check.metadata.comparisonSource`, `counterpartiesCompared` and `observedTransactionUrl` fields remain. The legacy `getSenderCounterparties` array accessor is retained, but consumers making decisions must migrate to coverage-aware `getSenderHistory`. Evidence exposes chain, transaction hash, direction, relationship, exact raw amount, optional token/log index/block/time, and initiator semantics. Replay rendering must distinguish configured references, observed relationships, missing coverage, research-supplied references and simulations. Never represent a proposed payment as broadcast or a research case as a live discovery. The original recorded research evidence is unchanged.
