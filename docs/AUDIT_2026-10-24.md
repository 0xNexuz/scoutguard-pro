# ScoutGuard PRO — release audit, 2026-10-24

## Current state and scope

Audited GitHub `main` at `eb8221a` (the latest commit at audit start), including the API, Blockscout client, payment normalizer, policy and receipt logic, mock agent adapter, replay archive/UI, tests, CI, deployment manifests, and public README. The [baseline GitHub Verify run](https://github.com/0xNexuz/scoutguard-pro/actions/runs/40118723515) succeeded. This audit also implemented and locally verified the two access-control fixes below.

**Verdict:** suitable for a transparent hackathon demonstration and bounded public evaluation. It is **not** evidence of safe unattended real-money agent execution. Current fresh anonymous Blockscout/Explorer behavior, distributed quotas, and a real signer were outside this local test. No provider credits, wallet transaction, or Craftora submission were used.

## Findings and fixes

| Priority | Finding | Impact | Resolution and proof |
| --- | --- | --- | --- |
| High — fixed | One `SCOUTGUARD_SERVICE_KEY` could select any known `agentId`, including the higher-cap treasury policy. | A caller with the procurement service key could request a more permissive policy without another authorization boundary. | `src/index.ts` now binds the protected key to `SCOUTGUARD_AGENT_ID` (default procurement), rejects mismatches with 403 before provider work, and rejects unknown configured IDs at startup. `test/api.test.ts` covers protected mismatch, a configured treasury service, and public policy override. |
| Medium — fixed | `GET /api/counterparties` returned operator-configured names and addresses without authentication. | Future configured counterparties could be disclosed publicly. No production configured list was observed in this audit. | The route now uses the same service-key middleware as protected evaluation. Tests cover missing, wrong, and correct keys. |
| Medium — fixed | The README mixed release history, setup, judge instructions, and caveats in a long stream and contained an obsolete post-release verification sentence. | New users could miss the exact public/protected paths and the provenance limits. | Rewritten README with a three-mode judge path, genuine local replay screenshot, copyable setup/API examples, authorization contract, evidence limits, verification commands, and deployment caveats. |

No other confirmed exploitable Critical or High issue was identified in the inspected code. This is a source and local-behavior audit, not a formal penetration test.

## Remaining risks and priorities

- **P0 before unattended real-money execution:** integrate a real wallet boundary with chain, nonce, gas, idempotency, and transaction-authorization controls. The current adapter demonstrates binding and mock signing only. The unkeyed receipt digest is not an authenticated signature.
- **P1 for public scale:** implement a shared deployment-wide quota and budget for Blockscout usage. Current per-IP, aggregate, concurrency, cooldown, and spacing controls are process-local.
- **P1 for efficacy claims:** run fresh authorized provider checks and a measured historical poisoning corpus. The older Poison-Hunter reference was supplied to a conditional replay, not recovered by the prior live scan; prevention efficacy is unmeasured.
- **P1 for release proof:** verify anonymous deployed API behavior and Explorer destination content from a normal trusted network. The prior release has authenticated Vercel-assisted content/health evidence, not a fresh independent full flow.
- **P2 for repository hygiene:** add a LICENSE after the owner chooses terms. `package.json` says MIT, but no license file exists. GitHub Dependabot alerts returned “disabled” during this audit; CI's npm audit remains active.

## Real versus simulated

Live evaluations can request Blockscout data. Archived cases are partial transcriptions of earlier production results and replay without provider calls. The Poison-Hunter example is a conditional research replay. The five attack demonstrations and browser-provider responses are fixtures. The agent example signs only with a mock signer. None of these categories is evidence of an executed payment or a prevented historical loss.
